# Mobile Contribution Draft

## Mobile Methodology

The mobile component of FROMO was developed using Flutter to provide a consistent cross-platform experience across Android emulator devices and mobile web. The mobile app was designed around a map-first discovery flow, allowing users to browse nearby events before committing to registration, saving, booking, or payment. This decision was made because event discovery is most useful when users can first understand location, price, crowd level, accessibility, and event details without being blocked by authentication. Therefore, unauthenticated users can access the map and event detail pages, while protected features such as saved events, bookings, profile, and payment actions remain restricted to logged-in users.

The main mobile interface combines an interactive map with a draggable event list. Events are displayed as price pins or clustered markers depending on zoom level and event density. This reduces visual clutter when many events are close together, while still allowing users to zoom in and inspect individual events. The map also supports category filtering, future-event filtering, and an accessibility filter based on venue accessibility data. These features were introduced to improve usability and make the mobile interface more inclusive, especially for users who need wheelchair-accessible venues.

Event detail pages show key information such as event image, category, date and time, venue, remaining spots, AI summary, price, and booking/payment status. For free events, users can reserve directly. For paid events, the app creates a Stripe checkout session through the backend and opens the Stripe payment page. The mobile flow was extended to support payment status feedback, so paid and pending bookings can be communicated clearly to users.

The directions feature was changed from simply opening Google Maps to showing an in-app route on the mobile map. The app uses a routing API where available and falls back to an approximate route if routing fails. The route UI includes estimated walking time, distance, recenter controls, destination marker, route polyline, and turn-by-turn style route steps. This makes the experience feel more integrated and avoids sending users away from the application unnecessarily.

The mobile app was also deployed as a Flutter web build on Netlify, connected to the Render-hosted backend API. This allows QR codes from the web application to direct users to a mobile-sized web version of the app. The mobile web deployment was important because the project does not yet have an App Store or Google Play release, but still needs an accessible way for external users and evaluators to test the mobile experience.

## Mobile Evaluation

The mobile implementation was evaluated through static analysis, automated tests, emulator testing, and manual cross-device checks. `flutter analyze` was used to identify code quality and type-safety issues, while `flutter test` was used to verify unit and widget-level behavior. Additional tests were added for core mobile models, API/provider behavior, feedback prompt behavior, booking screen states, and narrow-screen event card rendering.

Manual testing was carried out on Android emulator devices, including Pixel-style devices, to check layout behavior, navigation, payment flow, event images, saved events, bookings, filters, and map interactions. Particular attention was paid to smaller screen constraints because the app relies heavily on map and list combinations, bottom navigation, draggable sheets, and event cards. Several UI issues were identified and improved during testing, including event image display in saved/booked lists, map marker density, category filtering, accessible filtering, payment status display, and route panel behavior.

The mobile web deployment was tested separately because browser behavior differs from the native Android app. This was especially important for payment redirection. Since Stripe checkout opens in a browser, the payment success and cancellation flow needs to return users to either the native app or the deployed mobile web app. The final design uses the web application as an intermediate redirect page and then sends users back to the Netlify mobile web page.

Overall, the mobile app achieved the core goal of allowing users to discover, inspect, save, book, and navigate to events from a mobile-first interface. However, some limitations remain. The payment return flow depends on correct deployment environment variables across Render and Netlify. The accessibility feature also depends on venue data quality, and if many venues are marked as not accessible or unknown, the filter may produce limited results. The in-app routing feature is functional, but future versions could improve it with more accurate wheelchair-friendly routing, live location updates, and clearer step-by-step navigation.

## Mobile Limitations and Future Work

Although the mobile implementation provides a strong prototype, several improvements are still possible. First, the app should eventually support a production native release through Google Play or the App Store, instead of relying mainly on APK distribution and mobile web deployment. Second, payment return handling could be improved through deeper native app link support, so successful Stripe payments open the exact booking page in the installed app. Third, accessibility data should be improved at the database level so the accessible filter can return more reliable results. Finally, the directions feature could be extended with live navigation, wheelchair-friendly route calculation, and clearer route warnings when only approximate routing is available.
