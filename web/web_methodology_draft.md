# Web Methodology

The web component of FROMO was built with React and Vite to provide a fast, browser-native experience for two distinct audiences from a single codebase: students discovering events and partners/organisers managing their listings. The interface is organised around the same map-first discovery philosophy as the mobile app — an interactive Leaflet map (rendered over CARTO basemap tiles sourced from OpenStreetMap data) sits alongside a filterable event feed, so users can evaluate location, price, busyness, and accessibility before committing to sign-in. Consistent with this, the discovery feed and event detail views are reachable without authentication, while saved events, bookings, and partner-only actions require a signed-in session.

Authentication and session management are handled through Supabase (email/password), while all domain data — events, venues, bookings, listings — is served exclusively by the FastAPI backend over a REST API. A single Axios client centralises this communication: a request interceptor reads the current Supabase session on every call and attaches its JWT as a bearer token automatically, so individual components never handle token logic directly. This separation keeps Supabase scoped strictly to identity, with the backend remaining the sole source of truth for business data.

The student-facing feed supports category filtering, a today/tomorrow date filter, and an accessibility filter driven by venue `is_accessible` data, mirroring the filtering options available on mobile. Because the events endpoint does not return accessibility data directly, the frontend enriches each event with accessibility information by cross-referencing the venues endpoint — first fetching only the venues actually present in the current batch of events, to avoid the truncation that occurs if a venue falls outside a single fixed-size page. A busyness heatmap overlays the map, using the same busyness-level calculation as the mobile client so a venue's crowd status stays consistent across platforms.

On the partner side, a separate layout (`PartnerLayout`) provides its own navigation shell distinct from the student header, with routes for listings management, analytics, and settings. Venue creation was extended with address-to-coordinate geocoding via the OpenRouteService (ORS) API: partners type an address and the app resolves and confirms the matched location, with a manual latitude/longitude entry available as a fallback for addresses ORS cannot resolve. The in-app directions feature follows the same pattern as mobile — walking (wheelchair-accessible profile where relevant) routes are drawn directly on the map using ORS, falling back to opening Google Maps when no ORS key is configured, so the feature degrades gracefully rather than breaking.

The web app also serves as the redirect target for Stripe checkout: because payment happens in-browser regardless of which client initiated it, a dedicated `CheckoutRedirect` page handles the success/cancel return from Stripe before routing the user back into the app.

The web application was deployed on Render (https://fromo-website.onrender.com), connected to the same Render-hosted FastAPI backend used by the mobile deployment. This gives evaluators and external users a directly accessible, no-install version of the full student and partner experience, and serves as the canonical target for the QR-code reservation flow generated from the event detail page.

# Web Evaluation

The web implementation was evaluated through automated component/unit testing and iterative manual testing during development. Vitest, together with React Testing Library and `@testing-library/user-event`, was used to test components, pages, context providers, and the API/service layer in a jsdom environment. Tests are colocated with the code they cover (`__tests__/` folders per module) and isolate units from real network/auth state by mocking the `AuthContext` and router hooks (e.g. `useNavigate`), so, for example, `EventCard`'s navigation behaviour can be verified for both signed-in and signed-out users without a real Supabase session. The current suite covers seven test files and sixty tests spanning components, pages, context, and library code.

A GitHub Actions workflow (`ci-web.yml`) runs on every push or pull request touching `web/**`, executing `npm ci`, the Vitest suite, and a production Vite build in sequence — catching both logic regressions and build-breaking errors before merge. During development, this caught several real regressions that unit tests alone might have missed silently, including a venue-accessibility data truncation bug once the venue count passed a fixed page size, and a mismatch between the web and mobile busyness calculations that was corrected to keep both clients consistent.

Manual browser testing was used throughout to validate map/list interaction, pagination behaviour (the feed was moved from a hardcoded result limit to an explicit "Load More" pagination flow), scroll-position handling on navigation, and the partner venue-creation geocoding flow. Because the student and partner surfaces share a codebase but present very different UIs, particular attention was paid to ensuring partner routes render their own layout correctly rather than inheriting student-facing chrome.

Overall, the web app meets its core goal of letting students discover, filter, save, and book events, and letting partners create and manage venues and listings, from a browser with no installation required, deployed and reachable at https://fromo-website.onrender.com. Some limitations remain, discussed below.

# Web Limitations and Future Work

Several areas remain open for improvement. First, the production build currently emits a single JavaScript bundle exceeding Vite's 500KB size-warning threshold (measured at ~685KB minified); code-splitting the partner dashboard from the student discovery flow via dynamic `import()` would reduce the initial load for the more frequently used student surface. Second, the accessibility filter is only as reliable as the underlying venue data — as on mobile, if a large share of venues are marked as not accessible or unknown, filtered results will be sparse. Third, the in-app directions and venue-geocoding features depend on an external OpenRouteService API key with a limited free-tier quota (2,000 requests/day); at scale this would need to move behind the backend with caching, as already noted as a deferred item in the project's own documentation. Fourth, authentication gating is currently implemented ad hoc at the component level (e.g. individual click handlers checking `useAuth()`) rather than through a centralised route-guard pattern, which is functional but would benefit from consolidation as more protected routes are added. Finally, testing is currently limited to unit/component level; there is no end-to-end test suite (e.g. Playwright or Cypress) exercising a full user journey — such as sign-up through booking — across real routing and API calls.
